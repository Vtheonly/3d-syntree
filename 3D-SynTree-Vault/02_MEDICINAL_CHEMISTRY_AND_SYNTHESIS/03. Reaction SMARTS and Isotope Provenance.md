# 03. Reaction SMARTS and Isotope Provenance

### 1. What It Is

Reaction SMARTS is a computational string language that defines chemical transformations by matching substructures (reactants) and specifying the resulting structure (products). Isotope provenance is the technique of tracking individual atoms through chemical reactions using isotopic mass labels, preserving their identity even when RDKit rewrites atom indices during reaction execution.

Together, these form the mechanism by which 3D-SynTree executes chemical reactions while maintaining the connection between a product's atoms and their original 3D coordinates in the protein binding pocket.

### 2. Why It Exists

RDKit's `RunReactants` function is powerful but destructive to coordinate information. When a reaction runs:
1. Leaving groups are deleted (e.g., –OH leaves during amide coupling)
2. Internal atom indices are renumbered
3. The connection between product atoms and their source reactants is lost

Without isotope provenance, after reacting a core scaffold with a synthon, the model would not know which product atoms came from the core (and thus retain their pocket coordinates) versus which came from the synthon (and need new 3D embedding). This would break scaffold anchoring—the core would drift away from the protein pocket.

### 3. How It Works

#### SMARTS Format

SMARTS (SMiles Arbitrary Target Specification) extends SMILES with query features:

```
[Reactant 1].[Reactant 2]>>[Product]
```

- Atom brackets `[...]` define query constraints
- Atom maps `:n` track atoms across the transformation
- Recursive SMARTS (`!$(...)`) define negative constraints
- H-count predicates (`!H0`, `!H3`) control hydrogen counts

Example amide coupling SMARTS:
```
[C:1](=[O:3])[OH].[N;!H0;!H3;!$(NC=O):2]>>[C:1](=[O:3])[N:2]
```

This reads: A carbon (:1) double-bonded to oxygen (:3) with an OH group, reacts with a nitrogen (:2) that has hydrogens (not H0, not H3) and is not already an amide. Product: :1 double-bonded to :3, single-bonded to :2.

#### Isotope Tagging

Before reaction execution:
1. Core scaffold atoms receive isotope label `1000 + i` (where i is the atom index)
2. Synthon atoms receive isotope label `2000 + j` (where j is the atom index)

Isotopes survive RDKit's reaction execution without changing chemical behavior (RDKit preserves isotope labels on mapped atoms). After the reaction:
- Product atoms with isotope 1000+i came from the core → retain pocket coordinates
- Product atoms with isotope 2000+j came from the synthon → need new 3D embedding

The isotope tags are then cleared from the final product molecule.

### 4. What It Consists Of

| Component | Description |
|-----------|-------------|
| SMARTS | Query language for substructure matching and reaction definition |
| Atom mapping (`:n`) | Labels tracking individual atoms through transformations |
| Recursive SMARTS (`!$(...)`) | Negative constraints (e.g., "not already an amide") |
| H-count predicates (`!H0`, `!H3`) | Hydrogen count constraints for parser compatibility |
| Isotope tag | Mass label (e.g., 1005 for core atom index 5) |
| `_CORE_MAP_OFFSET` | Constant 1000 for core scaffold tagging |
| `_SYNTHON_MAP_OFFSET` | Constant 2000 for synthon tagging |
| `core_atom_map` | Dictionary mapping product atoms to core indices |
| `synthon_atom_map` | Dictionary mapping product atoms to synthon indices |

### 5. What You Must Understand

- **Isotopes do not change chemistry.** A carbon-13 behaves identically to carbon-12 in a reaction. The isotope label is purely a bookkeeping device for tracking provenance.

- **Mapped atoms survive; unmapped atoms are recreated.** In RDKit's reaction execution, atoms with atom maps are carried into the product with their identities preserved. Atoms without maps are created as new objects, losing all prior associations.

- **Isotope offsets prevent collisions.** Core tags (1000+i) and synthon tags (2000+j) occupy separate ranges, so no two atoms from different sources receive the same label.

- **The tag-to-coordinate mapping enables scaffold anchoring.** After reaction, the conformer engine uses `core_atom_map` and `synthon_atom_map` to know which product atoms should be held fixed (core) and which are free to embed (synthon).

- **Common pitfall:** Forgetting to clear isotope tags after use. Isotope labels affect molecular mass and some descriptors, so they must be removed from the final product before downstream processing.

- **Common pitfall:** Using atom-map numbers instead of isotopes for provenance. RDKit rewrites atom-map numbers during `RunReactants`, destroying the mapping. Isotope labels are preserved.

### 7. Project Connection

The SMARTS and isotope provenance concepts map directly to the 3D-SynTree codebase:

- **`apply_reaction()`** in `syntree/chemistry/reactions.py`: Executes a reaction template on core and synthon molecules, applying isotope tags before reaction and reading maps after.

- **`_tag_atoms()`** in `syntree/chemistry/reactions.py`: Assigns isotope labels `1000 + i` to core atoms and `2000 + j` to synthon atoms before reaction execution.

- **`_build_result()`** in `syntree/chemistry/reactions.py`: Constructs the product molecule, reads `core_atom_map` and `synthon_atom_map`, and clears isotope tags.

- **`ConformerEngine.embed_product()`** in `syntree/chemistry/conformer.py`: Uses the atom maps to anchor core atoms in pocket coordinates and embed only the new synthon atoms.

### 8. Required Depth

**Essential.** Without isotope provenance, 3D-SynTree cannot maintain scaffold anchoring during 3D conformer generation.
