# 05. Stationary Terminal Reward Formulation

### 1. What It Is

The **stationary terminal reward** is a key requirement for GFlowNet training: the terminal reward R(s_T) must depend only on the final state (the completed molecule), not on the trajectory that produced it or on other molecules in the batch.

This means:
- **Stationary:** The reward function doesn't change during training
- **Terminal:** The reward is given only at the end of an episode
- **State-dependent:** R(s_T) depends only on the final molecule, not the path

### 2. Why It Exists

GFlowNet detailed balance requires that F(s_T) = R(s_T). If the reward depends on anything other than the final state:

- **Batch-dependent rewards** (e.g., batch diversity) violate detailed balance because R depends on other molecules in the batch
- **Path-dependent rewards** violate the Markov assumption
- **Non-stationary rewards** make the learning target constantly moving

For 3D-SynTree, this means all reward components must be computable from the final molecule alone.

### 3. How It Works

#### Valid Terminal Reward Components

Each component must be computable from the final molecule:

| Component | Computable from final molecule? | Stationary? |
|-----------|--------------------------------|-------------|
| Docking score | Yes (dock the final molecule) | Yes |
| Contact energy | Yes (compute LJ/vdW with pocket) | Yes |
| Clash penalty | Yes (check steric overlaps) | Yes |
| QED drug-likeness | Yes (compute from molecular graph) | Yes |
| Key interactions | Yes (check specific residue contacts) | Yes |
| Batch diversity | NO (depends on other molecules) | NO |

#### Invalid: Batch Diversity

The batch diversity reward:
$$R_{\text{div}}(\mathcal{M}_i) = \frac{1}{|\mathcal{B}| - 1} \sum_{j \ne i} (1 - T(\mathcal{M}_i, \mathcal{M}_j))$$

depends on all other molecules in the batch. This makes R depend on batch composition, violating stationarity.

### 4. What It Consists Of

| Component | Description |
|-----------|-------------|
| Stationary reward | Reward independent of training batch and path |
| Terminal reward | Reward given at episode end |
| State-dependent | Depends only on final molecule |
| Batch diversity | Batch-dependent reward (violates stationarity) |
| Detailed balance | Requires stationary terminal reward |
| Issue #30 [FLOW-02] | 3D-SynTree issue addressing batch diversity removal |

### 5. What You Must Understand

- **Batch diversity cannot be in the terminal reward.** It depends on other molecules, making the reward non-stationary and breaking detailed balance.

- **Diversity can still be encouraged.** Through replay buffer sampling, curriculum design, or post-hoc filtering—but not through the terminal reward.

- **All reward components must be pre-computable.** Before training, you must be able to compute R(s_T) for any molecule without knowing the training batch.

- **Common pitfall:** Adding batch-dependent terms to the reward "to encourage diversity." This breaks the GFlowNet theoretical foundation.

- **Common pitfall:** Using reward shaping that depends on intermediate states. The reward must be terminal only.

### 7. Project Connection

The stationary terminal reward concepts map directly to the 3D-SynTree codebase:

- **`ThreeDReward`** in `syntree/engine/rl.py`: Computes terminal reward from docking score, contact energy, clash penalty, QED, and key interactions.

- **`batch_diversity()`** in `syntree/engine/rl.py`: Currently computes batch-dependent diversity reward—flagged for removal per Issue #30 [FLOW-02].

- **Issue #30 [FLOW-02]**: GitHub issue specifying removal of batch-relative metrics from terminal reward.

- **Reward weights** in `syntree/engine/rl.py`: Configurable weights for each reward component.
